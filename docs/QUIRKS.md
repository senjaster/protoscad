# Голые фигурные скобки не создают область видимости

Например
```
x = "Original message";
module my_mod() echo(x);
{
    x = "Message inside bare brackets";  
    union() {
        x = "Message inside any module invocation";  
        my_mod();
    }
}
```

Этот код выводит Message inside bare brackets, логика следующая
1) сначала x присваивается значение "Original message"
2) Поскольку фигурные скобки не создают область видимости, то та же переменная x переопределяется 
   значением "Message inside bare brackets". (и выдается ворнинг, переопределяеть плохо)
3) Внутри union() создается новая локальная переменная x, которая скрывает глобальную, но не затрагивает ее значение.
   Поэтому при вызове my_mod() выводится "Message inside bare brackets" - значение из глобальной переменной

---
Аналогичное поведение наблюдается и при обращении к "детям из модуля"

```
module my_mod() { children(1); }

my_mod()
{
   echo("aaa");
   {
      echo("bbb"); // выполняется только это
      echo("ccc");
   }
}
```

Этот код выводит просто bbb, а не bbb и ccc, поскольку фигурные скобки просто раскрываются

Однако если добавить любой модуль, например union(), то выведется bbb и ссс:
```
module my_mod() { children(1); }

my_mod()
{
   echo("aaa");
   union() { // выполняется весь блок целиком
      echo("bbb");
      echo("ccc");
   }
}
```

В нашей реализации это поведение полностью поддерживается

# Переменные: правило «последнее определение + первая позиция»

Проверено на реальном OpenSCAD (вывод echo/warning):

```
y = x; x = 10;            // WARNING: unknown 'x', y == undef
x = 1; y = x; x = 10;     // y == 10 (!) — y видит ПОСЛЕДНЕЕ x
x = 2; b = 1; y = b + x; x = 3;  // y == 4 — финальные b и x
b = 1; y = b + x; x = 2;  // y == undef — x впервые определён ПОЗЖЕ y
m = 5; union() { y = m; m = 1; }  // y == 5 — m ещё «не объявлен» локально,
                                  // срабатывает родительский m
q = zz; q = 7;            // q == 7, zz НЕ жалуется: затёртое присваивание
                          // вообще не вычисляется
q = zz;                   // WARNING даже если q нигде не используется —
                          // привязки вычисляются жадно, при создании скоупа
cube_size = 5; cube(cube_size); cube_size = 20;  // куб 20 — аргументы вызова
                                                  // видят финальную карту
module m(v) echo(v); m(w); w = 3;  // v == 3 — то же для вызовов модулей
x = 1; y = x; x = y + 1;  // цикл: оба undef с ворнингами
```

Итоговое правило OpenSCAD для скоупа:
1. Для каждого имени вычисляется только ПОСЛЕДНЕЕ присваивание, жадно, при
   создании скоупа (порядок исходника не важен для вызовов модулей).
2. RHS присваивания видит ФИНАЛЬНОЕ значение тех переменных скоупа, чьё
   ПЕРВОЕ определение стоит не позже самого присваивания.
3. Переменная, чьё первое определение позже, резолвится в родительском
   скоупе (а там undef, если её нет нигде).
4. Циклы в финальных определениях OpenSCAD тихо превращает в undef.

Это поведение реализовано в `OpenScadResolver` (runtime/resolver.py), с
одной поправкой: вместо ворнингов/undef мы бросаем ValueError.

По умолчанию же работает `DeclarativeResolver` — letrec-семантика без
позиционного правила: скоуп это набор одновременных определений, порядок
строк не важен. Повторное определение заменяет уравнение (как в OpenSCAD),
имя, определённое в скоупе, затеняет родителя во всём скоупе
(`m=5; union(){ y=m; m=1; }` даёт y=1, а не 5), ссылки на себя читают
родителя (`width = width/2`). Привязки ленивы (call-by-need, с
мемоизацией): неиспользуемый цикл не ошибка, а при форсировании
незащищённый цикл даёт ValueError с путём (`x -> y -> x`). Защищённые
циклы легальны: условие, которое не форсирует взятую ветку (например,
невзятая ветка тернарного оператора), разрывает цикл — как в Haskell/Nix.
Неизвестные имена в привязках отклоняются при создании скоупа, даже если
привязка не используется. Аргументы вызовов и тела модулей видят одну и
ту же карту значений.

# Три пространства имён: сосуществование и приоритет вызова

Переменная, функция и модуль с одним именем спокойно сосуществуют:
грамматическая позиция выбирает пространство имён — переменую, функцию 
или модуль.

Проверено на реальном OpenSCAD:

```
x = 2;                   // Определяем переменную
function x(x) = x + 1;   // Определяем функцию
module x(x) cube(x(x));  // Определяем модуль и внутри него вызываем функцию
x(x);                    // Вызваем модуль и передаем ему переменную
```

Функциональные литералы (OpenSCAD 2021+) добавляют к вызову в выражении
неоднозначность, поэтому появляется правило приоритета:

```
f = function(x) x + 2;
function f(x) = x + 1;
echo(f(1));  // Выводит 3 а не 2
```
Переменная с функциональным литералом имеет более высокий приоритет

Другой пример:
```
function f(x) = x + 1;
f = 10;
echo(f(1));  // 2 — переменная НЕ затеняет функцию
```

Правило: при вызове в выражении сначала проверяется переменная, и если она
содержит функциональный литерал — вызывается она; Если же в переменной обычное выражение,
то поиск продолжается среди функций.

Не проверяли: литерал во внешнем скоупе против функции во внутреннем;
вызов до текстового определения литерала.

Пространства имён видны и в импортах (по документации): use переносит
функции и модули, но НЕ переменные; include — всё подряд.

# `$`-аргументы на вызовах CSG-модулей: НАШЕ РАСХОЖДЕНИЕ с OpenSCAD

Проверено на реальном OpenSCAD:

```
module mysphere() {
    sphere(1);
    translate([3,0,0]) children();
}
union()
{
    mysphere($fn=360) sphere(1);  // две гладких сферы
}

let($fn=360) sphere(1);  // гладкая сфера

translate([0,0,0], $fn=360) sphere(1);  // гладкая сфера

union($fn=360) sphere(1);  // грубая сфера, то есть $fn не действует (!),

```

То есть в CSG-операциях (union, difference и т.п.) $-аргументы просто игнорируются, 
а во всех прочих случаях работают как объявление переменной $fn в let.
У пользовательских модулей $fn влияет как на тело, модуля так и на children().

У нас $fn всегда влияет на всех потомков, то есть и пример c union() вернет 
гладкую сферу.

Расхождение зафиксировано тестом `test_divergence_builtin_special_args_reach_children`
(tests/test_ast_evaluator.py); согласованные случаи — тестами
`test_user_module_special_args_match_openscad` и `test_let_special_args_match_openscad`.
